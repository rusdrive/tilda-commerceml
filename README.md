# Каталог Tilda через CommerceML: что работает, а что нет

Разбор того, как на самом деле ведёт себя приём CommerceML 2 в Tilda, и рабочий клиент
на чистом Python без зависимостей.

Официальной документации по реализации Tilda нет — поддержка это подтвердила прямым
текстом: «Более подробной документации нет, к сожалению». Справочный центр описывает
настройку обмена с 1С, но не отвечает на вопросы вроде «что будет с товарами, которых
нет в выгрузке» или «почему изображение не меняется». Здесь собраны ответы, полученные
опытным путём на живом магазине с каталогом в 1366 товаров, плюс то, что удалось
выяснить у поддержки.

## Зачем это нужно

Каталог магазина на Tilda обычно правят руками или скриптом, который ходит по внутренним
адресам `store.tilda.ru` с cookies залогиненного браузера. Второй способ работает, но
сессия протухает (у нас — трижды за один рабочий день), а сами адреса нигде не описаны и
могут измениться в любой момент.

CommerceML — публичный стандарт обмена с 1С, который Tilda поддерживает официально.
Логин и пароль вместо cookies, никакого браузера, и обновление Tilda его не сломает.

## Быстрый старт

```bash
cp config.example.json config.json   # вписать логин и пароль коннектора
python3 probe.py connect             # проверить связь, каталог не трогает
python3 test_local.py                # прогнать клиент через поддельный сервер
```

Логин, пароль и адрес коннектора: Каталог товаров → ••• → Синхронизация через
CommerceML.

```python
from cml_client import CommerceML
from cml_xml import build_import_xml, build_offers_xml

products = [{"id": "ART-001", "sku": "ART-001", "name": "Товар",
             "description": "Основной текст карточки"}]
offers = [{"id": "ART-001", "sku": "ART-001", "name": "Товар",
           "price": 1000, "quantity": 5}]

c = CommerceML()
c.send_catalog(import_xml=build_import_xml(products, "2026-09-05"),
               offers_xml=build_offers_xml(offers, "2026-09-05"))
```

## Для чего это хорошо подходит

### Обновлять цены по прайсу поставщика

Самый частый случай. Прайс приходит файлом, пересчитали наценку — и отправили весь
каталог одним запросом, без единого клика.

```python
from cml_client import CommerceML
from cml_xml import build_offers_xml

offers = [{"id": art, "sku": art, "name": name, "price": price, "quantity": qty}
          for art, name, price, qty in rows_from_price_list]

CommerceML().send_catalog(offers_xml=build_offers_xml(offers, "2026-09-05"))
```

Тысячи позиций уходят одним обменом. Товары, которых нет в списке, не затрагиваются —
можно слать только изменившиеся.

### Держать остатки в актуальном состоянии

То же самое, но по расписанию. Логин с паролем не протухают, поэтому обмен спокойно
живёт в cron и не требует, чтобы кто-то был залогинен в браузере.

```python
offers = [{"id": art, "sku": art, "name": name, "price": price,
           "quantity": stock.get(art, 0)} for art, name, price in catalog]
CommerceML().send_catalog(offers_xml=build_offers_xml(offers, today))
```

Нулевой остаток убирает товар из продажи (а если в магазине включено скрытие товаров не
в наличии — и с витрины).

### Заводить новые товары пачкой

Выгрузка от поставщика превращается в карточки: название, артикул, тексты, раздел,
характеристики и фотографии — всё за один проход.

```python
from cml_xml import build_import_xml

products = [{
    "id": art, "sku": art, "name": name,
    "description": text,                       # основной текст карточки
    "requisites": {"Полное наименование": short},  # краткое описание
    "group_id": "section-1",
    "properties": {"Бренд": brand, "Вес": weight_g,   # вес в ГРАММАХ
                   "Длина": l_mm, "Ширина": w_mm, "Высота": h_mm},
    "image": ["import_files/1.jpg", "import_files/2.jpg"],
}]
```

Фотографии заливаются файлами перед импортом — см. раздел про изображения. Помните, что
новый товар публикуется сразу.

### Массово править тексты в существующих карточках

Например, добавить всем товарам раздела строку про доставку или переписать описания по
новому шаблону. Через интерфейс это сотни однотипных действий, здесь — один проход.

```python
products = [{"id": art, "sku": art, "name": name,
             "description": new_text} for art, name, new_text in edits]
CommerceML().send_catalog(import_xml=build_import_xml(products, today))
```

### Заполнить вес и габариты для расчёта доставки

Частая дыра в каталогах: без веса служба доставки считает по максимуму. Передаётся
свойствами, вес в граммах, размеры в миллиметрах.

```python
products = [{"id": art, "sku": art, "name": name,
             "properties": {"Вес": "1200", "Длина": "300",
                            "Ширина": "200", "Высота": "150"}}]
```

### Связать магазин со своей учётной системой

Если товары живут в вашей базе, CRM или самописной админке, обмен закрывает
одностороннюю выгрузку в магазин целиком: создание, цены, остатки, тексты. Ключ связи —
`<Ид>`, кладите туда свой постоянный идентификатор.

### Когда лучше не это

- **Разовая правка одной карточки** — быстрее руками в интерфейсе.
- **Нужны SEO-поля, метка или несколько разделов** — обмен их не передаёт, нужен CSV.
- **Надо снять товар с продажи или удалить** — только вручную.
- **Надо заменить фото у существующего товара** — пока не работает.

## Как устроен обмен

Шесть запросов в одной HTTP-сессии, состояние держится в cookie, которую сервер выдаёт
на первом шаге:

```
?type=catalog&mode=checkauth   вход (HTTP Basic) → success + имя и значение cookie
?type=catalog&mode=init        → zip=no, file_limit=3145728
?type=catalog&mode=file        залить import.xml (тело запроса = содержимое файла)
?type=catalog&mode=file        залить offers.xml
?type=catalog&mode=import      импорт первого, ответ progress → повторять
?type=catalog&mode=import      импорт второго
```

**Статус приходит первой строкой тела, а код ответа всегда 200.** По HTTP-коду судить
об успехе нельзя — даже на «Auth required» приходит 200.

**На импорте реально приходит `progress`.** Нужно повторять тот же запрос, пока не
придёт `success`, иначе решите, что обмен провалился.

## Что можно

| Поле | Как передаётся |
|---|---|
| Название | `<Наименование>` |
| Основной текст карточки | `<Описание>` |
| Краткое описание | реквизит `Полное наименование` (уходит и в `meta description`) |
| Артикул | `<Артикул>` |
| Цена, остаток | `offers.xml` |
| Характеристики | `<ЗначенияСвойств>` |
| Бренд | свойство с именем `Бренд` или `Производитель` |
| Вес, габариты | свойства `Вес`, `Длина`, `Ширина`, `Высота` |
| Раздел (один) | `<Группы>`, сопоставление **по названию** |
| Изображения | файлом, **только при создании товара** |

Всё это, кроме изображений, обновляется и у существующих товаров.

## Чего нельзя

| Что | Подробности |
|---|---|
| Удалить товар | `<ПометкаУдаления>` принимается с `success`, товар остаётся. Поддержка подтвердила: только вручную |
| Скрыть товар с витрины | нельзя; косвенно — нулевым остатком, если в магазине включено скрытие товаров не в наличии |
| SEO-заголовок, описание, ключевые слова | перебрано 15 написаний реквизитов, ни одно не работает. Поддержка: «только CSV» |
| Отметка на карточке (метка NEW) | то же самое, только CSV |
| Несколько разделов у товара | передаётся ровно один. В планах Tilda есть, сроков нет |
| Заменить или добавить фото существующему товару | восемь способов, все впустую; см. ниже |
| Зачёркнутая старая цена | два набора типов цен не сработали: Tilda берёт первый как основной, `oldprice` остаётся пустым. Перепроверено отдельно — обмен при этом рабочий, цена меняется. Поддержка говорит, что старая цена передаётся; способ выяснить не удалось |

Недостающее приходится доливать импортом CSV, у которого есть колонки
`External ID, Mark, Category, Parent UID, SEO descr, SEO keywords`. Причём `Category`
принимает несколько разделов через `;`. **Загрузить CSV программно нельзя** — поддержка
подтвердила, только вручную через интерфейс.

## Грабли, на которых легко потерять день

### Имя файла обмена должно быть в формате 1С

Самая дорогая ловушка из всех. Tilda обрабатывает только имена вида `import0_N.xml` и
`offers0_N.xml`. Файл с любым другим именем она принимает с `success` и на импорт тоже
отвечает `success`, но **не делает ничего**. Проверено на двух вариантах: и на
`import0_20260905181811.xml`, и на простом `import.xml` — оба обмена в логе Tilda
помечены как отменённые.

Снаружи обмен выглядит безупречно: все шесть шагов зелёные. Понять, что происходит,
можно только по логу в интерфейсе Tilda, где остаётся:

```
Импорт товаров отменён.
```

Признак исправного обмена — ответ **`progress`** на импорте. Если Tilda сразу отвечает
`success`, не начав обработку, скорее всего файл до неё не дошёл.

Так выглядит обмен, который действительно сработал (подробный лог в интерфейсе Tilda):

```
Принят файл: import0_1.xml
Принят файл: offers0_1.xml
Запущена обработка полученных файлов.
Найдено товаров: 1, предложений: 1.
Создан товар "…".
Импорт товаров завершен.
```

А в истории синхронизации у неудачных остаётся одна строка — «Импорт товаров отменён».

Отдельно бывает, что повторный импорт под тем же именем отклоняется как
`failure / Import file is empty`, хотя файл не пустой. Лечится не выдумыванием своего
имени, а увеличением номера: `import0_2.xml`, `import0_3.xml`. Клиент в этом
репозитории так и делает.

### Есть ограничение по частоте обменов

После нескольких десятков обменов подряд коннектор начинает отвечать:

```
failure
Many requests. Please try again
```

Причём отбивается уже `checkauth` — то есть до файлов дело не доходит. Рядом могут
появляться и невнятные `Import error` на нормальных файлах: это тот же лимит, просто
на другом шаге. Лечится паузой, а не повтором — повторы делают только хуже.

Точных цифр Tilda не публикует. Для регулярной работы это не помеха (обмен раз в
несколько минут проблем не вызывает), но при отладке, когда обмены идут один за другим,
в лимит упереться легко.

### У Tilda есть лог синхронизации, и он честнее ответов сервера

Каталог → ••• → Синхронизация через CommerceML → история и подробный лог. Там видно,
какие файлы реально приняты и чем закончился импорт. Мы потеряли на этом несколько
часов, доверяя ответам `success`, — лог показал правду за минуту.

### Товары, которых нет в выгрузке, не затрагиваются

Можно смело слать один товар, а не весь каталог. Проверено снимками до и после на
каталоге в 1366 позиций при **всех включённых** галочках импорта: изменений у чужих
карточек — ноль. Поддержка подтвердила это же словами.

### Раздел ищется по названию, а не по идентификатору

`<Ид>` группы роли не играет. Раздела с таким названием нет — Tilda **создаст новый**.
То есть опечатка в названии не даёт ошибку, а молча плодит разделы в каталоге.

### `<Ид>` товара — это внешний код, а не артикул

`<Ид>` попадает во внешний код (External ID) и служит ключом связи между обменами.
Видимый артикул карточки берётся из отдельного тега `<Артикул>`. Если слать в оба тега
одно значение, разницу не заметить — мы так и попались.

### Вес в граммах, размеры в миллиметрах

Tilda пересчитывает: свойство `Вес` со значением `1000` даёт 1 кг, а `Длина` со
значением `100` — 10 см. Ошибка здесь даёт вес в тысячу раз неверный и сломанный расчёт
доставки.

### Новый товар публикуется сразу

Не черновиком. Заводя тестовый товар, ставьте нулевой остаток — иначе он окажется на
витрине.

### Изображения — только файлом и только при создании

Ссылка в `<Картинка>` не работает: приходит `success`, изображений ноль. Картинку надо
залить тем же `mode=file` под именем вида `import_files/фото.jpg`, а в XML указать этот
относительный путь.

При создании товара это работает, в том числе несколько фото сразу (несколько тегов
`<Картинка>`, первый — главный). А вот у товара, где фото уже есть, заменить или
добавить его не удалось ни одним из семи способов:

| Что пробовали | Результат |
|---|---|
| Ссылка вместо файла | не работает даже при создании |
| Файл под тем же именем | картинка не меняется |
| Файл под уникальным именем | картинка не меняется |
| Путь с подпапкой, как в примере 1С | картинка не меняется |
| Несколько тегов `<Картинка>` существующему товару | лишние отбрасываются |
| `СодержитТолькоИзменения="false"` | картинка не меняется |
| Уникальное имя у самого файла обмена | картинка не появляется |

| Всё то же самое на заведомо рабочем обмене | картинка не меняется |

Последняя строка важна: часть попыток мы проделали, не заметив, что наш же клиент шлёт
файлы под неправильными именами и Tilda их отменяет (см. ловушку с именами ниже). Поэтому
проверку повторили начисто — завели товар, дождались первой картинки, отправили вторую.
Результат тот же.

Каждый раз сервер отвечает `success`. Поддержка утверждает, что обновлять изображения
можно, и передала вопрос разработчикам — ответа на момент публикации нет. **Если вы
знаете рабочий способ, напишите в issues.**

### Фид YML обновляется не сразу

Около 10 минут после обмена. Ускорить можно переопубликацией сайта. Проверять результат
раньше бессмысленно.

## Проверка результата

Отдельная беда — убедиться, что обмен реально что-то сделал. `success` не доказывает
ничего: половина неудачных попыток в таблице выше отвечала успехом.

Что помогает:

- смотреть лог синхронизации в интерфейсе Tilda — он показывает, что она сделала
  на самом деле, а не что ответила по HTTP;
- считать признаком работы ответ `progress` на импорте: мгновенный `success` без
  него подозрителен;
- сравнивать снимки каталога до и после (`probe.py snapshot`, затем `probe.py diff`);
- искать изображение по **количеству** тегов `<picture>`, а не по имени файла — Tilda
  перезаливает картинки к себе под своими именами;
- не добавлять параметры к адресу карточки при проверке: на любой параметр приходит
  редирект с пустым телом, и проверка будет смотреть в пустоту;
- проверять, что скачанный фид распарсился — он отдаётся обрезанным чаще, чем кажется.

Все четыре пункта — грабли, на которых мы сами постояли.

## Три слоя защиты перед боевым запуском

`success` от Tilda не доказывает, что каталог обновился — она отвечает успехом и на
обмен, который потом сама же отменяет. Поэтому в `cml_safety.py` есть три проверки,
которые стоит поставить вокруг обмена.

**1. Валидация — данные вообще пригодны?**

```python
from cml_safety import validate
errors = validate(products, offers)
if errors:
    raise SystemExit("\n".join(errors))
```

Ловит пустые и повторяющиеся `<Ид>`, пустые названия, отрицательные цены и остатки,
нечисловой вес, управляющие символы. Одна ошибка в исходной базе иначе уедет в каталог
как есть.

**2. Предохранители — не слишком ли много меняем разом?**

```python
from cml_safety import plan, format_plan, fetch_snapshot
before = fetch_snapshot(yml_url)
report, tripped = plan(before, offers)
print(format_plan(report, tripped))
if tripped:
    raise SystemExit("остановлено предохранителем")
```

Печатает, что произойдёт, и останавливает обмен при подозрительном размахе:

```
будет создано товаров: 3
изменится цена:        48
обнулится остаток:     121
  резкий скачок цены — ART-2: 1000 → 100 (90%)

ОСТАНОВЛЕНО предохранителем:
  обнулений остатка 121, порог 50
```

Пороги по умолчанию: 10 новых товаров, 100 изменений цены, 30% на одну цену,
50 обнулений остатка. Поднимаются осознанно через `limits=`.

**3. Проверка результата — а изменилось ли что-нибудь?**

```python
after = fetch_snapshot(yml_url)      # через 10 минут: фид обновляется не сразу
status, lines = verify(before, after, offers=offers, products=products)
```

Статусы: `verified` — всё подтвердилось, `partial` — применилась часть, `failed` —
не изменилось ничего, `pending` — выгрузка ещё не пересобралась, `unknown` — нечего было
проверять. Именно это отличает «Tilda ответила успехом» от «каталог действительно
обновился».

`pending` важен отдельно: выгрузка обновляется около десяти минут, и проверка сразу
после обмена без него давала бы ложную тревогу на каждом запуске. Отличаем по атрибуту
`date` у `yml_catalog` — если он тот же, судить рано. Для расписания есть готовое
ожидание с предельным сроком:

```python
status, lines = wait_and_verify(yml_url, before, offers=offers, max_wait=1200)
sys.exit(EXIT_CODES[status])
```

`EXIT_CODES` даёт ненулевой код на любой неуспешный исход — `partial`, `failed`,
`pending`, `unknown`, лимит частоты, непрошедшую валидацию, сработавший предохранитель.
Планировщик заметит это сам, без разбора логов.

Для защиты от параллельных запусков есть файловый замок:

```python
with single_instance():
    ...обмен...
```

Два одновременных обмена взяли бы одинаковые имена файлов и могли перемешаться.

Отдельно клиент распознаёт лимит частоты: на `Many requests` бросается `RateLimitError`
и повторы не запускаются — помогает только пауза.

### Артефакты каждого запуска

Когда через неделю в каталоге найдётся что-то странное, важно иметь возможность
посмотреть, что и когда мы отправляли, а не вспоминать.

```python
from cml_safety import RunRecorder
rec = RunRecorder()
rec.save_plan(report, tripped, before=before)
rec.save_files(**{"import0_1.xml": import_xml, "offers0_1.xml": offers_xml})
rec.save_exchange(client.log)
rec.save_verification(status, lines, after=after)
sys.exit(rec.finish())
```

Складывает в `runs/20260905-153500/`: сам план с применёнными порогами, отправленные
файлы как есть, ответы сервера по шагам, вердикт проверки и короткий `summary.txt`.
Плюс контрольные суммы файлов, даты выгрузки до и после, версия кода по commit hash.

Пароль и заголовок `Authorization` туда не попадают — клиент их в лог не пишет
(проверяется тестом). Каталог `runs/` в git не уходит.

## Чего этот клиент пока НЕ делает

- **повтор при `Import file is empty` переотправляет обмен целиком** — дубликатов из-за
  стабильного `<Ид>` не будет, но лишняя нагрузка и неопределённость при частично
  завершённом обмене есть;
- **варианты товара не поддерживаются** — только простые товары; поддержка Tilda
  говорит, что через обмен они передаются, но здесь это не реализовано и не проверено;
- **остаток один на товар**, склады не поддерживаются;
- **нет отправки только изменившегося** — шлём то, что дали;
- **нет уведомлений** — код возврата есть, а отправку письма или сообщения в мессенджер
  надо навесить снаружи.

Позиционирование честное: это проверенный клиент для контролируемого обмена с одним
магазином, а не универсальная промышленная библиотека.

## Файлы

| Файл | Что делает |
|---|---|
| `cml_client.py` | протокол: шесть шагов, cookie сессии, ожидание `progress`, разбиение файла по `file_limit` |
| `cml_xml.py` | сборка `import.xml` и `offers.xml` |
| `probe.py` | пошаговая проверка на живом каталоге: от безвредных шагов к записи |
| `cml_safety.py` | три слоя защиты: валидация, предохранители, проверка результата |
| `test_local.py` | прогон клиента через поддельный сервер, без обращения к Tilda |
| `test_safety.py` | проверки трёх слоёв защиты |
| `config.example.json` | образец настроек |

Зависимостей нет, только стандартная библиотека Python 3.

## Ответы поддержки Tilda

Дословно по сути, сентябрь 2026:

- при синхронизации передаются: заголовок, описание, цена (старая и новая), количество,
  варианты товара и их свойства, артикул, раздел, характеристики;
- свойства с именами `Бренд`, `Производитель`, `Длина`, `Ширина`, `Высота`, `Вес`
  заполняют соответствующие поля товара;
- SEO-параметры и отметку на карточке передать нельзя, для этого нужен CSV;
- несколько разделов сейчас не поддерживаются, в будущем возможно;
- загрузка CSV — только ручная;
- удалить товар через синхронизацию нельзя, только вручную;
- товар, которого нет в выгрузке, не затрагивается;
- новый товар публикуется сразу, а не черновиком.
